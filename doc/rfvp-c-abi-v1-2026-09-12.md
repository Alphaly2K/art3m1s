# RFVP C ABI v1 设计说明

日期：2026-09-12

状态：设计稿，尚未由 RFVP 构建导出。

对应头文件：

- [rfvp_api_v1.h](abi/rfvp_api_v1.h)

本文取代早期的
[rfvp_render_host_v1.h](abi/rfvp_render_host_v1.h)。旧方案使用反向 callback
表，RFVP 调用 Host；新方案沿用 `art3m1s-core` 的版本化函数表和对象句柄模型，
Host 主动调用 RFVP，跨边界只传递句柄、标量和 POD 数据。

## 核心约束

一句话规则：**对象走句柄，数据走裸指针。**

- runtime、frame、resources 都以非零 `uint64_t` 句柄表示。
- `set_render_quality_preset`、lifecycle、frame acquire/release、resource
  mount/override 等对象操作只接收句柄和标量。
- 顶点、像素、uniform/effect block、pack 字节、JSON/翻译文本使用
  `const uint8_t * + size_t`，或者由 RFVP 持有的定长 POD 数组。
- v1 不让 Dart FFI 按值传递复杂复合结构。函数参数只有整数、浮点、指针和
  长度；结构体只通过指针暴露。
- 输入数据在函数返回后是否可释放，由函数注释明确；Host 侧输入资源通常由
  RFVP 同步复制。

## 入口与版本校验

最终唯一新增的平铺导出符号是：

```c
const RfvpApiV1 *rfvp_get_api_v1(size_t *out_size);
```

Host 必须依次校验：

1. 返回指针不为空；
2. `abi_version == RFVP_API_ABI_VERSION`；
3. `magic == RFVP_API_ABI_MAGIC`；
4. `struct_size` 不小于 Host 已知的最小前缀；
5. 每个准备调用的函数指针不为空。

函数表只允许追加字段。已有字段的偏移、类型和语义不能改变。函数指针为空表示
该能力未实现，Host 不得因为表存在就假定能力存在。

当前设计的函数表大小固定为编译时 `RfvpApiV1` 的大小；没有函数则填 `NULL`。
这样可以先完成 Host 侧探测和 adapter 编译，再逐项接实现。

## 句柄

```c
typedef uint64_t RfvpHandleV1;
#define RFVP_INVALID_HANDLE UINT64_C(0)
```

句柄实现不能直接暴露 Rust `Box`/`Arc` 地址。推荐使用进程内 typed registry：

- 低 32 位保存 slot index；
- 高 32 位保存 generation；
- 删除后 generation 递增，防止 ABA；
- 0 永远无效；
- 每个句柄类别在 Rust 侧使用独立类型，避免 runtime/frame/resources 混用。

句柄不是并发许可。v1 要求同一个 resources/runtime/frame 只在创建它的线程上
串行访问；Host 如果要并发，必须在自家 bridge 层加锁和队列。

## Resources 对象

Resources handle 持有 RFVP 的资源视图和存档根：

```c
rfvp_resources_create(config, &resources);
rfvp_resources_mount_directory(resources, path, len);
rfvp_resources_mount_pack(resources, folder, folder_len, blob, blob_size);
rfvp_resources_set_override(resources, path, path_len, data, data_size);
rfvp_resources_clear_overrides(resources);
rfvp_resources_set_save_root(resources, path, path_len);
rfvp_resources_clear(resources);
rfvp_resources_destroy(resources);
```

约定：

- `nls` 决定 pack 文件名和 HCB 文本编码；
- `mount_directory` 接受 UTF-8 路径字节，不要求 NUL；
- `mount_pack` 同步复制 pack 字节，函数返回后 Host 可以释放输入；
- `set_override` 同步复制数据，适合补丁文件和资源覆盖；
- 多份 mount 和 override 的查找顺序必须稳定；同一路径最后设置的 override
  优先；
- `clear` 清空 mounts 和 overrides，但保留 resources 对象和 save root；
- resources 必须比引用它的 runtime 活得久；
- v1 不复用 `art3m1s-core` 的 `HostResources`，两者文件命名空间不同。

## Runtime 对象

`RfvpRuntimeConfigV1` 只携带 resources 句柄和初始尺寸，不携带裸路径：

```c
typedef struct RfvpRuntimeConfigV1 {
    uint32_t struct_size;
    uint32_t flags;
    uint64_t resources;
    uint32_t requested_width;
    uint32_t requested_height;
    uint64_t reserved[4];
} RfvpRuntimeConfigV1;
```

基本时序：

```text
resources_create
    -> mount_directory / mount_pack / set_override
    -> runtime_create({ resources, ... })
    -> runtime_push_input
    -> runtime_step
    -> runtime_acquire_frame
    -> frame_get_*
    -> frame_release
    -> ...
    -> runtime_destroy
    -> resources_destroy
```

```c
rfvp_runtime_step(runtime, delta_ms);
rfvp_runtime_is_exit_requested(runtime);
rfvp_runtime_push_input(runtime, events, event_count);
rfvp_runtime_set_render_quality_preset(runtime, preset);
rfvp_runtime_set_media_enabled(runtime, enabled);
rfvp_runtime_notify_lifecycle(runtime, state);
rfvp_runtime_set_volume(runtime, channel, value);
rfvp_runtime_poll_audio_command(runtime, &command);
rfvp_runtime_capabilities(runtime);
rfvp_runtime_destroy(runtime);
```

- `runtime_step` 只推进逻辑和资源状态，不负责 present。
- `runtime_push_input` 输入是 POD 数组，调用返回后 RFVP 不再引用该数组。
- `runtime_is_exit_requested` 返回 1/0，不自动销毁 runtime。
- `runtime_destroy` 释放所有属于该 runtime 的未释放 frame。
- `set_render_quality_preset` 的取值与 `art3m1s-core` 对齐：
  `0 Native`、`1 Quality`、`2 Balanced`、`3 Performance`。

### 音频输出

RFVP host-runtime 不创建 Kira、CoreAudio、WASAPI 或 ALSA 设备。BGM/SE 的加载、
播放、停止、音量和 pan 统一转换成 `RfvpAudioCommandV1`：

```c
RfvpAudioCommandV1 command;
int32_t status = rfvp_runtime_poll_audio_command(runtime, &command);
if (status == RFVP_STATUS_OK) {
    /* command.payload 在下次 poll 或 runtime_destroy 前有效 */
}
```

- `RFVP_STATUS_NO_COMMAND` 表示当前没有音频命令；
- `stream_id` 保留 RFVP 逻辑槽位：BGM=`0..255`，SE=`0x1000..0x10ff`；
- encoded load 的 payload 是原始压缩音频字节；
- PCM submit 的 payload 是小端 `i16` 或 `f32`；
- Host 负责设备创建、解码器复用、轨道生命周期、暂停/恢复和实际输出。

## Frame 借用

Frame 是一个短生命周期对象，不是第二份 runtime：

```c
uint64_t frame = 0;
int32_t status = rfvp_runtime_acquire_frame(runtime, &frame);
if (status == RFVP_STATUS_OK) {
    uint32_t width, height;
    const RfvpTextureCommandV1 *textures;
    size_t texture_count;
    const RfvpDrawCommandV1 *commands;
    size_t command_count;
    const RfvpHitProxyV1 *hit_proxies;
    size_t hit_proxy_count;

    rfvp_frame_get_size(frame, &width, &height);
    rfvp_frame_get_textures(frame, &textures, &texture_count);
    rfvp_frame_get_commands(frame, &commands, &command_count);
    rfvp_frame_get_hit_proxies(frame, &hit_proxies, &hit_proxy_count);

    /* apply textures first, then draw commands */
    rfvp_frame_release(frame);
}
```

生命周期规则：

- 一个 runtime 同时最多借出一个 frame；
- 已借出 frame 时再次 acquire 返回 `RFVP_STATUS_BUSY`；
- `frame_get_*` 返回的指针归 frame 所有，直到 `frame_release`；
- frame 释放后，所有先前返回的指针立即失效；
- frame 和 runtime 必须在同一线程串行使用；
- 没有新画面时 acquire 返回 `RFVP_STATUS_NO_FRAME`。

Frame 数据分为三个只读列表。Host 必须先应用 texture commands，再处理 draw
commands。这样同一帧新上传的纹理可以被同一帧的 draw command 引用。

## 纹理命令

创建、更新、销毁使用同一个 tagged POD：

```c
typedef struct RfvpTextureCommandV1 {
    uint32_t struct_size;
    uint32_t kind;
    uint32_t texture_id;
    uint32_t format;
    uint32_t width;
    uint32_t height;
    uint32_t mip_count;
    uint32_t row_bytes;
    RfvpRectI32V1 rect;
    uint64_t generation;
    const uint8_t *pixels;
    size_t pixels_size;
    uint64_t reserved[2];
} RfvpTextureCommandV1;
```

语义：

- `CREATE`：创建或完整替换 `texture_id`。`pixels_size` 必须覆盖完整纹理；
- `UPDATE`：替换 `rect` 指定的子区域，`row_bytes` 表示源数据每行字节数；
- `DESTROY`：释放纹理；此时 pixels 为 `NULL`，`pixels_size == 0`；
- `generation` 随同一 `texture_id` 的新像素版本递增；
- 相同 `(texture_id, generation)` 的重复 CREATE 可由 Host 去重；
- `RFVP_TEXTURE_ID_WHITE` 是保留的 1x1 白色纹理 id；
- 纹理 id 是 runtime 内的值，不是跨引擎的对象句柄。

v1 只承诺 `RGBA8` 和 `LumaA8`。如果以后增加 RGB565、索引色和移动端
压缩纹理，只能追加新枚举值，不能改变已有像素布局。

## Draw 命令

Draw command 是定长 POD，四条内联顶点覆盖常见 quad：

```c
typedef struct RfvpDrawCommandV1 {
    uint32_t struct_size;
    uint32_t kind;
    uint32_t flags;
    uint32_t texture_id;
    uint32_t blend;
    uint32_t filter;
    uint32_t effect_id;
    uint32_t mesh_topology;
    RfvpRectU16V1 src_rect;
    RfvpRectI32V1 dst_rect;
    RfvpRectI32V1 clip_rect;
    RfvpColorV1 color;
    RfvpVertexV1 vertices[4];
    const RfvpVertexV1 *mesh;
    size_t mesh_vertex_count;
    const uint8_t *effect_data;
    size_t effect_data_size;
    uint64_t reserved[2];
} RfvpDrawCommandV1;
```

映射到 `art3m1s-render` 的路线：

- `RFVP_DRAW_IMAGE`：普通纹理 quad；`vertices` 已包含位置、UV 和顶点色；
- `RFVP_DRAW_GLYPH`：同一 quad 路径，语义上标记为 glyph；
- `RFVP_DRAW_SOLID`：使用保留 white texture 的实色 quad；
- `HAS_MESH`：`mesh/mesh_vertex_count` 是展开后的三角形或 strip；Host
  可转换成 `DrawMesh`，不需要先回到 RFVP 内部 primitive；
- `HAS_CLIP`：`clip_rect` 是像素空间矩形，Host 转成后端 scissor；
- `HAS_EFFECT`：`effect_id` 选择语义，`effect_data` 是定长 POD/uniform
  block，按 `effect_id` 解释；
- v1 不把 `art3m1s-render::DrawCommand` 的 Rust 对象直接跨边界传递。

这层设计保留了顶点缓冲和 uniform block 的零拷贝读取，同时让 Host 在
`art3m1s-render` 内完成纹理、mesh、effect 和 resource cache 管理。

## HitProxy

Hit proxy 是独立的 frame-owned POD 数组：

```c
typedef struct RfvpHitProxyV1 {
    uint32_t prim_id;
    uint32_t flags;
    RfvpRectI32V1 rect;
    uint32_t order;
    uint32_t reserved0;
} RfvpHitProxyV1;
```

`order` 越大越靠前；只有 `ENABLED` 且 `VISIBLE` 的代理参与命中。Host 不应把
hit proxy 当成可写输入，写回输入必须使用 `runtime_push_input`。

## 事件

事件传输沿用 `art3m1s-core` 的“先查大小，再轮询完整事件”模型：

```c
size_t size = rfvp_runtime_next_event_size(runtime);
size_t written = rfvp_runtime_poll_events(runtime, out, capacity, &count);
```

- v1 事件按 runtime 隔离，不使用 core 当前的进程级全局队列；
- 队列为空时 `next_event_size` 返回 0；
- `poll_events` 只写完整事件，不写半条；
- 容量不足时保留队首事件，返回 0；
- `sequence` 单调递增；
- 事件 header 的字节布局与 `art3m1s-core` 一致：24 字节；
- 事件类型值也保留 core 的 `1=log, 2=media, 3=UI, 4=text_translation`，
  但 RFVP 的 payload 协议独立定义。

日志事件 payload 是 UTF-8 字节，`aux` 为等级首字符，例如 `D/I/W/E`。
媒体和 UI 事件值先保留，v1 暂不承诺完整 payload 协议。

### 文本翻译

`RFVP_EVENT_TEXT_TRANSLATION` 的 payload：

```text
RfvpTextTranslationEventV1
+ source_utf8[source_len]
+ ruby_utf8[ruby_len]
```

```c
typedef struct RfvpTextTranslationEventV1 {
    uint32_t struct_size;
    uint32_t encoding;
    uint64_t serial;
    uint64_t generation;
    uint32_t slot;
    uint32_t source_offset;
    uint32_t source_len;
    uint32_t ruby_offset;
    uint32_t ruby_len;
    uint32_t reserved0;
} RfvpTextTranslationEventV1;
```

Host 处理流程：

1. 读取 source/ruby；
2. 交给现有 `TextTranslationService`；
3. 回填 `rfvp_runtime_submit_text_translation(runtime, serial, bytes, len)`；
4. RFVP 校验 serial 和 slot generation；过期结果返回失败，不覆盖新文本。

替换表通过独立入口提交：

```c
rfvp_runtime_set_text_replacements(runtime, blob, size, encoding);
rfvp_runtime_set_text_translation_enabled(runtime, enabled);
```

`encoding = RFVP_SERIALIZATION_JSON` 时，blob 是 UTF-8 JSON 对象，键和值都是
字符串。RFVP 同步复制 blob；Host 返回后即可释放。

## 错误

成功统一为 `RFVP_STATUS_OK == 0`。`NO_FRAME` 是正常状态，不是错误。
负值才会映射失败：

| 状态 | 含义 |
| --- | --- |
| `INVALID_ARGUMENT` | 指针、长度、枚举或数值非法 |
| `INVALID_HANDLE` | 句柄为 0、类型错误、已销毁或 generation 过期 |
| `INVALID_STATE` | 当前生命周期不允许该操作 |
| `NOT_FOUND` | 资源、纹理或请求不存在 |
| `INVALID_DATA` | pack、JSON、UV、像素格式等数据无效 |
| `UNSUPPORTED` | 当前构建或平台未实现 |
| `OUT_OF_MEMORY` | 分配失败 |
| `BUSY` | 一个 runtime 已有未释放 frame，或对象被占用 |
| `IO` | 文件读写失败 |
| `ENGINE` | RFVP/VM/后端返回的未细分错误 |

`poll_events` 和 `next_event_size` 使用 `size_t` 返回字节数；无事件为 0。
句柄无效和容量不足在当前设计中都表现为 0，Host 应先维护自己的句柄生命周期，
不要把 0 解释成具体错误。

## Dart FFI 映射

Host 侧建议：

- handle、sequence、generation 使用 `ffi.Uint64`；
- count、id、枚举使用 `ffi.Uint32/Uint64`；
- `size_t` 按目标平台映射到 `ffi.UintPtr`；
- 字符串、像素、pack、uniform 用 `ffi.Pointer<ffi.Uint8>` 加长度；
- frame 结构体只使用 `Pointer<RfvpDrawCommandV1>` 等指针读取；
- `RfvpApiV1` 只在启动时解析一次并缓存函数指针；
- 不把结构体按值传给 native，也不让 native 返回结构体值。

这与用户强调的规则一致：Dart FFI 对复杂结构体 by-value 的支持有限，而当前
ABI 的调用形态基本全是 `Int64/Int32 + Pointer + size`。

## v1 明确不做

- 不把 Rust trait object、`Arc`、`Box` 或 GPU handle 直接跨边界；
- 不让 Host 持有 RFVP `Vec` 所有权；
- 不支持一个 frame 跨线程延迟消费；
- 不把 `art3m1s-core` 的 `CoreRuntime`/`HostResources` 类型混进 RFVP API；
- 不用旧 `rfvp_run_entry`、`rfvp_pump_*`、`rfvp_ios_*`、
  `rfvp_android_*` 的签名承载新协议；
- v1 冻结前不允许修改已有字段类型、顺序、枚举值或错误值。
